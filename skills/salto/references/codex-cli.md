# Codex CLI notes (read only in Codex CLI)

SKILL.md tells Codex CLI to read this file first. Other agents don't need it. These notes add to SKILL.md and the workflow files, and they win where they differ.

- `<SKILL_DIR>` is the folder that holds this skill's SKILL.md: the `<path>` Codex gave in the `<skill>` block, or the skill's `file:` path in the skills list with its root (`r0`, `r1`, ...) replaced by the full path from the "Skill roots" table, without `/SKILL.md`. Read every bundled file by its full path under it. A relative path such as `references/salto-deploy.md` resolves against the project, not the skill.
- `$ARGUMENTS` in the skill files means the user's request: the text sent with `$salto-cli-skills:salto` (or the message that made you use this skill), including flags such as `--workspace`, `--deployment-id` or `--branch-name`.
- The Codex sandbox blocks the network and keeps the repo's `.git` folder read-only. `salto-cli` calls Salto over the network, and git commands that change the repo (`add`, `commit`, `push`, `worktree`) write `.git`. So run every `salto-cli` command, every `gh` command, and those git commands with sandbox escalation (`sandbox_permissions: "require_escalated"`) on the first try, with a short justification such as "Run salto-cli preflight (needs network)". Run read-only commands (`git status`, `git diff`, `ls`, `grep`, `cat`) in the sandbox. Don't ask for escalation for anything else.
- Inside the sandbox, `salto-cli` reports the blocked network as "Authentication Failed" ("Your token may be expired") and `gh` says it is not logged in. If a command that ran in the sandbox says this, run it again with escalation before you treat it as an auth error. Don't tell the user to change their token because of a sandboxed run. If escalation isn't possible (for example `codex exec`, or approval policy `never`), stop and tell the user that Salto deploys need Codex's approval prompts (see "Start Codex for Salto" in the plugin README).
- In the DEPLOY workflow, make every NACL edit with your file-edit tool (`apply_patch`) inside `WORKTREE_PATH` (from `salto-cli deployment prepare-worktree`), never in the user's workspace folder. `WORKTREE_PATH` is next to the workspace, outside Codex's writable folder, so Codex asks the user to approve these edits; that is expected. Write the PR body to `<STATE_DIR>/pr-body.md` with the same tool.
- If the user declines an approval, or a command still fails because of the sandbox or approvals, stop: end your turn and tell the user what you need and why. Don't look for another way around it: never edit the user's working tree instead, never write files with shell commands (heredoc, `echo`, `python`, `cp`, ...), and never re-run a declined command in another form.
- Never install or run `salto-cli` with `npx` or `npm`: Salto doesn't publish it on npm, so anyone could publish a package with that name. If `salto-cli` is missing, stop and ask the user.
